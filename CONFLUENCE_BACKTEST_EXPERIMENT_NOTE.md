# Confluence Min-Score Threshold — Historical Backtest Evidence

**Experiment ID:** `confluence-min-score-threshold-recalibra-2026-08-15T2354200000`
**Registry stage reached this cycle:** `historical_testing` (see `experiment_registry.jsonl`)
**Status:** Evidence gathered and registered. **No live config was changed.** Next stage (`walk_forward_testing`) is explicitly not run yet — this note ends with that as the recommended next step, decision reserved for the platform owner.

---

## Why this exists

`engine/qualification_diagnostics.py` (shipped earlier this cycle) found the live platform had **zero trade approvals across all 4 symbols for 9+ consecutive tracked days**, with 82% of rejections attributed to the `confluence_assessment` / `weak_evidence` gate — i.e., signals scoring below `confluence_min_score = 70` (`engine/confluence.py`, `DEFAULT_MIN_SCORE`).

That raised an obvious question the codebase had never actually answered: **has the 70-point threshold itself ever been backtested?**

It turned out no. `engine/backtest.py` calls only `engine/signals.py`'s Layer-1 analysis — it never invokes `engine/confluence.py` at all. The exact filter responsible for the live 9-day drought had never been run against historical data.

## What was built

`engine/confluence_backtest.py` (new, additive, 18 tests in `tests/test_confluence_backtest.py`) bridges the gap: it replays each trade `backtest.py` already generated through `confluence.analyze()` at that trade's exact historical decision point (using the same lookback window backtest.py itself uses), records the score and tier confluence would have assigned, then buckets trades by threshold to show what would have qualified at each cutoff. `compare_thresholds()` reuses `backtest.summarize()` unmodified for aggregation, so the win-rate/expectancy/profit-factor/drawdown math is identical to the platform's existing, trusted backtest math — only the admission filter changes.

## The run

- **Data:** `data/XAU_15m_data.csv` — the only symbol with local historical data (WTIUSD/BTCUSD/EURUSD untested).
- **Window:** last 40,000 bars, 2023-09-13 to 2025-09-30 (~2 years).
- **Trades replayed:** 416, generated by `backtest.py`'s existing signal-scan logic.
- **Replay integrity:** 416/416 replayed cleanly — 0 direction/entry mismatches between confluence's re-derived signal and backtest's original signal, 0 errors.

**Evidence sufficiency by sample size** (`engine/evidence_tiers.py`): thresholds 0–65 (n=115–184) reach `production_ready_evidence`; 70–80 (n=35–86) reach `moderate_confidence`; 85 (n=18) is only `preliminary_evidence`.

## Key finding

Expectancy is **not monotonic** in confluence score. The 50–55 bucket beats the live 70 default on both expectancy (+0.30R vs +0.24R) and trade count (161–171 vs 86) — and thresholds ≥75 collapse toward zero edge, the opposite of what a well-calibrated quality score should show at its high end. On this sample, the live threshold is cutting into the score's own sweet spot rather than filtering toward it.

## Caveats (read before acting on this)

1. **Single symbol, single in-sample window.** No walk-forward/out-of-sample split has been run. This is exactly why the registry stage is `historical_testing`, not `walk_forward_testing` — in-sample results routinely overstate OOS performance.
2. **`backtest.py`'s own known limitations carry through unchanged** — no slippage modeling, fixed `$0.30` spread assumption (see `RESEARCH_VALIDATION_SPECIFICATION.md`).
3. **`portfolio_risk.evaluate()` is excluded entirely.** Live approvals also depend on drawdown protection, correlation, and session gates not modeled here.
4. **Methodology note:** `confluence.analyze()` internally re-derives its own Layer-1 signal at `signals.WATCH_THRESHOLD` (55) rather than reusing backtest's signal at `PUBLISH_THRESHOLD` (70). Empirically this caused zero mismatches on this dataset, but that's not guaranteed on other symbols/periods.
5. **The n=18 (score≥85) bucket is below `evidence_tiers.MIN_N_FOR_TRUST` (30)** — its near-zero expectancy is suggestive, not independently trustworthy.

## Recommendation

Do not change `confluence_min_score` in live config from this evidence alone. Next step per the registry's own lifecycle: run walk-forward (expanding-window, out-of-sample) validation at `min_score=55` — success bar suggested in the registered hypothesis is OOS expectancy >= +0.20R at n>=30 OOS trades, with drawdown not worse than the current live threshold's own recent -12R figure. If that holds, and ideally after replicating on a second symbol once more historical data is available, the threshold change becomes a decision for you to make and approve — not one this system will make on its own.
